## The longer story (so you would feel what my story behind doing this assignment)

### 1. Indexes

An index works like the index at the back of a book: without one, MongoDB reads every document to find a match (a `COLLSCAN`), and with the right one it jumps straight to it (an `IXSCAN`). The starter created no indexes at all, so every lookup, list and report read the whole collection, and rules like "one record per employee per day" or "a duplicate employee gives 409" had nothing in the database enforcing them. Instead of guessing, I wrote down every query the API makes and what it filters and sorts on, then gave each shape one index, always putting exact-match fields first and the sort or range field after. On `employees` that gave me a unique `emp_code` (lookups and duplicate creates), `department + emp_code` (the filtered list and the trend) and `joined_on + department` (the department summary). On `attendance_logs` it gave a unique `emp_code + date` (punch-in, PATCH, monthly and trend), `date` descending + `emp_code` (the list sort and the leaderboard) and `emp_code + punch_in` descending (punch-out). They are all created at startup with `create_index`, which does nothing if the index already exists, so restarting is safe. Running explain on a 100k-record load test caught one real gap: the department summary started with a `joined_on` range that no index covered, so I added `joined_dept`. I rejected a plain `emp_code` index, because `emp_code + date` already starts with it and an extra index only slows down writes.

### 2. Punch-in race

The contract says that when two identical punch-ins arrive at the same moment, exactly one gets 201 and the other gets 409, and it warns against check-then-insert. The starter did exactly that: `find_one`, then `insert_one`. I traced what happens with two requests: both run `find_one` before either has inserted, both see nothing, and both insert, leaving two records for one day. Making the Python check faster would never close that gap, because two separate steps can always interleave. I realised the only place that handles the two requests strictly one at a time is the database, so it should be the referee, and a unique index on `(emp_code, date)` is exactly that kind of rule. In my code both requests look up the employee, work out the same attendance date and build the same document, then go straight to `insert_one` with no `find_one` first. MongoDB accepts the first insert into the unique index and rejects the second with a duplicate-key error, which I catch as `DuplicateKeyError` and return as 409 "already punched in for this date". The insert is all or nothing, so the losing request leaves nothing half-written behind. I didn't want to just trust the theory, so I wrote `race_test.py`, which fires ten identical requests in parallel against Atlas, and every run gave one 201 and nine 409s. I then used the same "let the database decide" idea for punch-out and for PATCH.

### 3. Ties on the leaderboard

The late leaderboard ranks employees by total late minutes in the month, and the contract asks for standard competition ranking, where ties share a rank and the next rank is skipped: 1, 2, 2, 4. While reading it, I noticed two traps. The rank must not simply be the row's position in the list, and `limit` applies after ranking, so if three people tie at rank 2, `limit=2` has to return all four rows, not just two. To be sure I understood it, I built test data with a deliberate tie: one employee 45 minutes late, three at 30, one at 20, and a late log for an employee who doesn't exist. I worked out the expected answer by hand first: 1, 2, 2, 2, 5, with the unknown employee left out. In the pipeline I rank with `$setWindowFields` and `$rank`, sorting only on total late minutes. If I had added `emp_code` there as a tie-breaker, the tied people would no longer look equal and would get different ranks, and MongoDB 8 actually refuses a second sort key for `$rank`. After ranking I keep every row whose rank is at most `limit`, and only then sort by total minutes and `emp_code`, so tied people always come out in the same order. So when two employees tie at the cutoff, both are returned with the same rank, even if that means more rows than `limit`.

### 4. Headcount with zero logs

The department summary reports a headcount: everyone who had joined by the end of the month, whether or not they have any attendance logs. My first thought was to group the logs by department, but I soon saw that this can never work, because someone with no logs would simply never appear in the result. Headcount is about people, so the query has to start from people. To check my design, I followed one employee with zero logs through every stage of the pipeline. After the `$lookup` they have an empty `logs` array, and a plain `$unwind` deletes documents with empty arrays, which is exactly where they would vanish. I also saw the opposite problem for everyone else: unwinding creates one row per log, so counting rows would count the same person many times. My pipeline starts from `employees`, keeps only those who joined by month end, looks up their logs for that month, and unwinds with `preserveNullAndEmptyArrays: true`, so a zero-log employee survives as one row without a log. When grouping by department, I collect the unique `emp_code`s with `$addToSet` and use the size of that set as the headcount. A zero-log row adds 0 to every other total, because its status check is false. I tested January and June 2026, where nobody has logs: each department still shows the right headcount with zeros elsewhere, and a department where nobody had joined yet is left out, as the contract asks.

### 5. One thing I would change at 100x the data

The API is comfortable at 100k records, so the real question was what would hurt first at around ten million. Rather than guess, I went back to the explain output from my 100k load test and compared, for each query, how many rows it returned with how many index keys it had to read. Most queries read about as many keys as they returned, which is the ideal case. One stood out: page 50 of the attendance list read 5,000 index keys to return just 100 rows. The cause is `skip`: MongoDB cannot jump to row 4,901, so it walks past every skipped row first, and the deeper the page, the more it reads. At 100x the data, deep pages would get slower and slower, even though every query in the explain checks shows a clean `IXSCAN`. I would replace `skip` with range (cursor) paging: the response includes the last `(date, emp_code)` it returned, the client sends that back, and the next query starts right after it in the `date_desc_emp_code` index I already have. Every page then costs about the same, however deep it is, and no new index is needed. The next thing on my list would be an index for status-only filters, because counting the `total` for something like `?status=LEAVE` currently has to go through every record.
